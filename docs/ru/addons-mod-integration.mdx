# Аддон как интеграция с другим модом

Аддон HollowEngine может быть прослойкой между HE и другим Minecraft-модом, если целевой мод
предоставляет публичный runtime API. Такая прослойка может принимать события целевого мода,
преобразовывать его модель в стабильный контракт HollowEngine, вызывать его сервисы из команд,
скриптов и UI, а также синхронизировать нужное состояние через addon packets.

Базовая структура проекта, descriptor и полный lifecycle описаны в
[основном руководстве](./addons.mdx).

Главный критерий — **обратимость**. Всё, что интеграция регистрирует после старта игры, должно быть
возможно снять до закрытия addon classloader. Если целевой API не позволяет unregister, требует
Mixin или участвует в ранней регистрации контента, одного hot-swappable аддона недостаточно.

## Что реально можно связать

| Возможность целевого мода | Реализация в аддоне |
| --- | --- |
| Публичный service/API singleton | Compile-only вызов через тонкий adapter |
| Event bus с unregister/token | Подписка с cleanup через `onUnload` |
| Команды или callback API | Reversible registration, если API позволяет удалить contribution |
| Чтение состояния мира | Перевод в стабильные DTO/сервис HE на правильном thread |
| Изменение состояния мира | Проверка прав и dispatch на server thread |
| Клиентский overlay/экран | Client addon + HE HUD/IDE extension points |
| Собственный сетевой протокол мода | Его публичный networking API либо отдельный HE addon packet |
| Новые блоки/items/entities/attachments | Companion-мод, потому что registry ранний |
| Mixin/access widener/access transformer | Companion-мод, загружаемый вместе с Fabric/NeoForge |
| Приватный API без официальной точки доступа | Сначала предложить upstream API; иначе companion Mixin/Accessor |

Не используй reflection для доступа к приватным полям и методам. Она хрупка относительно mappings и
версий, маскирует несовместимость и не решает lifecycle. Для необходимого раннего доступа сделай
обычный companion-мод с Accessor/Invoker Mixin, access widener или access transformer.

## Базовая архитектура адаптера

Рекомендуемая граница состоит из четырёх частей:

```text
Target mod public API
        │
        ▼
TargetModAdapter  ── owns target registrations
        │
        ▼
Stable HE-facing interface + DTO
        │
        ├── hostServices → other addons
        ├── HollowEngine events/commands/scripts
        ├── addon packets → client/server
        └── IDE/HUD extensions
```

`TargetModAdapter` — единственное место, импортирующее типы чужого мода. Остальная логика работает
с собственными интерфейсами и DTO. Это уменьшает область, которую придётся менять при обновлении
целевого API, и не позволяет чужим transient objects утечь в scripts, UI или другие аддоны.

Хороший HE-facing контракт:

- небольшой и ориентирован на возможности, а не на внутреннее устройство мода;
- использует immutable data и стабильные Minecraft/shared types;
- не возвращает внутренние collections, event instances, registries или implementation classes;
- явно описывает thread и logical side каждого метода;
- возвращает `AutoCloseable`/registration token для подписок;
- не передаёт наружу addon `CoroutineScope`, Koin или classloader;
- допускает появление новых полей/операций без breaking change.

## Обязательная интеграция

Если без целевого мода аддон бессмысленен, добавь его API только в compile classpath и потребуй
стабильный публичный class в descriptor.

```kotlin
repositories {
    maven("https://maven.example.com/releases")
}

dependencies {
    add("modCompileOnly", "com.example:claims-mod:4.2.0")
}
```

Если publisher предоставляет отдельный plain Java API artifact, используй `compileOnly` вместо
`modCompileOnly`. Никогда не помещай JAR самого мода в `addonLibraries` или
`addonBootstrapLibraries`.

```properties
id=claims-hollow-bridge
name=Claims integration for HollowEngine
version=${version}
entry=com.example.claimsbridge.ClaimsBridgeAddon
environment=common
requiredClasses=com.example.claims.api.ClaimsApi
```

Можно перечислить несколько classes через запятую. Проверка происходит до entrypoint и даёт
понятную причину в log вместо случайного `NoClassDefFoundError` внутри `load()`.

`requiredClasses` проверяет бинарное присутствие, но не mod ID и не semver. Если целевой API
публикует version/capabilities, проверь их в `load()` и упади с понятным сообщением до регистрации
внешних ресурсов.

## Пример двустороннего service adapter

Контракт аддона может выглядеть так:

```kotlin
import net.minecraft.core.BlockPos
import net.minecraft.resources.ResourceKey
import net.minecraft.world.level.Level
import java.util.UUID

interface ClaimsHeApi {
    fun owner(level: ResourceKey<Level>, position: BlockPos): UUID?

    fun observe(listener: (ClaimChange) -> Unit): AutoCloseable
}

data class ClaimChange(
    val level: ResourceKey<Level>,
    val position: BlockPos,
    val oldOwner: UUID?,
    val newOwner: UUID?,
)
```

Adapter напрямую знает целевой API, но наружу публикует только контракт выше:

```kotlin
import com.example.claims.api.ClaimsApi
import net.minecraft.core.BlockPos
import net.minecraft.resources.ResourceKey
import net.minecraft.world.level.Level
import java.util.UUID
import java.util.concurrent.atomic.AtomicBoolean

class ClaimsAdapter(
    private val target: ClaimsApi,
) : ClaimsHeApi, AutoCloseable {
    private val closed = AtomicBoolean()
    private val listeners = linkedSetOf<(ClaimChange) -> Unit>()
    private val targetRegistration = target.onClaimChanged { event ->
        listeners.toList().forEach { listener ->
            listener(event.toHeChange())
        }
    }

    override fun owner(level: ResourceKey<Level>, position: BlockPos): UUID? =
        target.findClaim(level, position)?.owner

    override fun observe(listener: (ClaimChange) -> Unit): AutoCloseable {
        check(!closed.get()) { "Claims adapter is closed" }
        listeners += listener
        return AutoCloseable { listeners -= listener }
    }

    override fun close() {
        if (!closed.compareAndSet(false, true)) return
        targetRegistration.close()
        listeners.clear()
    }
}
```

В реальном коде коллекция listeners должна соответствовать threading contract целевого event bus:
например, `CopyOnWriteArrayList` для concurrent callbacks или строгий server-thread ownership.

Entrypoint связывает lifecycle:

```kotlin
import com.example.claims.api.ClaimsApi
import kotlinx.coroutines.CoroutineScope
import ru.hollowhorizon.hollowengine.common.addons.HollowAddonContext
import ru.hollowhorizon.hollowengine.common.addons.HollowAddonEntrypoint
import ru.hollowhorizon.hollowengine.common.addons.extensions
import ru.hollowhorizon.hollowengine.common.addons.publish

class ClaimsBridgeAddon : HollowAddonEntrypoint {
    override suspend fun load(context: HollowAddonContext, scope: CoroutineScope) {
        val adapter = ClaimsAdapter(ClaimsApi.instance())
        context.extensions.onUnload(adapter::close)
        context.hostServices.publish<ClaimsHeApi>(adapter)
    }
}
```

Сначала регистрируется cleanup, затем service публикуется наружу. Если следующая операция упадёт,
rollback закроет adapter. Service runtime снимет автоматически; ручной `unpublish` не нужен.

Аддон-потребитель должен объявить `dependsOn=claims-hollow-bridge`. Тогда он увидит именно тот
`ClaimsHeApi`, который загружен classloader-ом provider, а provider выгрузится только после всех
потребителей.

## Опциональная интеграция

Если аддон полезен и без целевого мода, не указывай его class в `requiredClasses` и не помещай чужие
типы в поля, superclass, interfaces, constructor или сигнатуры entrypoint. Держи прямые imports в
отдельном adapter class, который загружается только после проверки mod ID.

```kotlin
import kotlinx.coroutines.CoroutineScope
import ru.hollowhorizon.hollowengine.common.addons.HollowAddonContext
import ru.hollowhorizon.hollowengine.common.addons.HollowAddonEntrypoint
import ru.hollowhorizon.hollowengine.common.addons.extensions
import ru.hollowhorizon.hollowengine.common.addons.publish
import ru.hollowhorizon.hollowengine.common.utils.ModList

class OptionalBridgeAddon : HollowAddonEntrypoint {
    override suspend fun load(context: HollowAddonContext, scope: CoroutineScope) {
        if (!ModList.isLoaded("claims")) {
            context.hostServices.log("Claims integration is inactive: target mod is not installed")
            return
        }

        val adapter = runCatching(::createClaimsAdapter).getOrElse { error ->
            context.hostServices.log("Claims integration is incompatible: ${error.message}")
            return
        }
        context.extensions.onUnload(adapter::close)
        context.hostServices.publish<ClaimsHeApi>(adapter)
    }
}
```

`createClaimsAdapter()` должен находиться в файле/class, изолирующем imports чужого API. Проверка
`ModList.isLoaded` не гарантирует совместимость версии; `LinkageError` означает, что adapter нужно
обновить под фактический API. Не продолжай работу в частично совместимом режиме, если это может
повредить данные.

`@RequireMod` применяется только к найденному `@SubscribeEvent` handler. Она удобна для
опционального HE event handler, но не заменяет изоляцию target classes и не отключает весь entrypoint.

## Потоки и события чужого мода

Не предполагай, что callback целевого мода приходит на server thread. Его API может использовать
render thread, network executor, worker pool или собственный scheduler.

Для асинхронного уведомления, после которого можно продолжить позже:

```kotlin
targetRegistration = target.observe { targetEvent ->
    val snapshot = targetEvent.toImmutableSnapshot()
    context.minecraft.dispatchers.executeServer {
        applyToWorld(snapshot)
    }
}
```

Не сохраняй исходный event object: после callback он может стать недействительным или удерживать
целый world/registry. Скопируй только нужные значения.

Если событие требует синхронного return value или cancellation, нельзя безусловно dispatch-ить его
асинхронно. Выполни короткую thread-safe проверку в callback либо используй официальный механизм
целевого мода для перехода на нужный thread. Блокировать worker и ждать server thread опасно
deadlock-ом.

Все фоновые collectors запускай в переданном addon scope. Если чужая библиотека создаёт собственный
thread/executor, adapter обязан закрыть его в `close()`.

## Сеть и logical sides

Сначала определи, где существует authoritative state:

- server integration читает и изменяет состояние целевого server-мода;
- client UI получает только разрешённый snapshot;
- client request всегда повторно валидируется сервером;
- addon packet не должен переносить implementation object чужого мода.

Если packet type зарегистрирован только аддоном, совместимый аддон должен быть установлен на обеих
сторонах соединения. Для server-only интеграции без client feature пакет может быть не нужен.

`environment` описывает **физическую** сторону. `server` не загрузится в integrated server, потому
что процесс физически является client. Если интеграция должна работать в singleplayer, обычно нужен
`common` entrypoint без безусловных client imports и явное разделение логической server/client работы.

Использовать сетевой API целевого мода стоит только когда он публичный, стабилен и позволяет runtime
registration. В остальных случаях стабильный `HollowAddonPacket` лучше изолирует HE-контракт, но
требует синхронной установки/версии bridge addon.

## Fabric и NeoForge

Стандартная addon convention создаёт named variant для NeoForge и remapped intermediary variant для
Fabric из одного общего source set. Это хорошо работает, когда целевой мод предоставляет одинаковый
публичный API на обеих платформах.

Если API отличаются:

1. сохрани общий HE-facing контракт;
2. вынеси platform implementation за отдельную границу;
3. не загружай Fabric classes на NeoForge и наоборот;
4. не определяй платформу через наличие случайного внутреннего class;
5. при значительном расхождении используй обычный двухплатформенный companion-мод.

Текущая стандартная convention аддона не предоставляет независимые `fabric` и `neoforge` source
sets для двух разных adapter implementations. Не усложняй runtime условными ссылками на loader
internals: companion-мод с тонкими Fabric/NeoForge adapters даёт более проверяемую архитектуру.

## Когда нужен companion-мод

Companion нужен, если интеграция требует хотя бы одного из следующих действий:

- зарегистрировать block/item/entity/menu/attachment или другой ранний объект;
- подключить Mixin config, access widener или access transformer;
- подписаться в loader phase, которой ещё нет при запуске addon runtime;
- предоставить разные Fabric и NeoForge реализации;
- получить доступ к закрытому API через поддерживаемый Accessor/Invoker;
- удерживать native/bootstrap dependency весь срок жизни игры.

Тогда архитектура делится так:

```text
Fabric companion ─┐
                  ├─ parent-loaded stable BridgeContract
NeoForge companion┘                 ▲
                                    │ compileOnly
                         hot-swappable HE addon
```

Stable contract объявляется в companion/API artifact, загружаемом родительским classloader. Он не
должен ссылаться на addon implementation types. Companion предоставляет reversible callback/service
API, а аддон владеет registrations и закрывает их при unload.

Mixin/accessor остаётся активным до завершения JVM, но addon behavior можно reload-ить, если
companion не кеширует callback после закрытия registration. Это честная граница hot-swap: ранний hook
стабилен, сменная логика — динамическая.

## Версии и отказоустойчивость

В текущем descriptor нет `minHostVersion`, диапазона версии target mod и optional `dependsOn`.
Поэтому integration addon должен:

- компилироваться против минимально поддерживаемого public API;
- делать feature/capability checks через официальный API;
- fail fast до публикации services, если обязательная capability отсутствует;
- сохранять собственные данные в versioned schema, а не сериализовать target implementation classes;
- игнорировать неизвестные новые enum/packet values безопасным образом;
- не обещать поддержку версии, которая проверялась только компиляцией;
- указывать совместимые HE/Minecraft/target versions в release notes.

Не используй «fallback через private reflection»: он превращает предсказуемую несовместимость в
скрытую ошибку данных. Лучше понятный `INACTIVE`/load failure и диагностическое сообщение.

## Checklist интеграции

Перед выпуском проверь:

1. целевой мод отсутствует;
2. минимальная и максимальная заявленные версии target API;
3. dedicated server, physical client и integrated server;
4. Fabric и NeoForge;
5. target callback приходит одновременно с disable/reload;
6. повторные load/unload не дублируют listeners, commands или services;
7. consumer addon выгружается до provider bridge;
8. новая версия bridge не может прочитать старое persistent state без миграции;
9. клиент отправляет некорректные/устаревшие packet data;
10. target mod сам перезагружает world/config/resources;
11. после нескольких reload нет новых threads и старых addon classloaders;
12. companion и addon с несовместимыми версиями дают понятную ошибку, а не частичную работу.

Итоговое правило простое: аддон подходит для динамической **логики и адаптации публичных runtime
API**. Всё, что меняет раннюю структуру игры или не имеет обратимой регистрации, должно остаться в
обычном моде или стабильном companion-слое.
