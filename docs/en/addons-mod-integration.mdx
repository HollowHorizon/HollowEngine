# Integrating another mod with an addon

A HollowEngine addon can bridge HE and another Minecraft mod when the target exposes a public
runtime API. The bridge can receive target events, convert its model into a stable HollowEngine
contract, invoke its services from commands, scripts, and UI, and synchronize selected state through
addon packets.

Project layout, descriptor fields, and the complete lifecycle are documented in the
[main addon guide](./addons.mdx).

The deciding property is **reversibility**. Everything registered after game startup must be removable
before the addon classloader closes. If the target API cannot unregister, requires a Mixin, or takes
part in early content registration, a hot-swappable addon alone is insufficient.

## What can be bridged

| Target-mod capability | Addon implementation |
| --- | --- |
| Public service/API singleton | Compile-only call through a thin adapter |
| Event bus with unregister/token | Subscription with `onUnload` cleanup |
| Commands or callback API | Reversible registration, when the API can remove contributions |
| Read world state | Translate into stable DTOs/HE service on the correct thread |
| Mutate world state | Permission checks and server-thread dispatch |
| Client overlay/screen | Client addon plus HE HUD/IDE extension points |
| Target's own network protocol | Its public networking API or a separate HE addon packet |
| New blocks/items/entities/attachments | Companion mod because registration is early |
| Mixin/access widener/access transformer | Fabric/NeoForge companion mod |
| Private API with no official access point | Request an upstream API first; otherwise companion Mixin/Accessor |

Do not use reflection to reach private fields and methods. It is fragile across mappings and
versions, hides incompatibility, and does not solve lifecycle ownership. Use a regular companion mod
with an Accessor/Invoker Mixin, access widener, or access transformer when early access is necessary.

## Adapter architecture

A recommended boundary has four parts:

```text
Target mod public API
        │
        ▼
TargetModAdapter  ── owns target registrations
        │
        ▼
Stable HE-facing interface + DTO
        │
        ├── hostServices → other addons
        ├── HollowEngine events/commands/scripts
        ├── addon packets → client/server
        └── IDE/HUD extensions
```

`TargetModAdapter` is the only place that imports foreign-mod types. All remaining logic uses local
interfaces and DTOs. This limits the surface changed by a target API upgrade and prevents foreign
transient objects from leaking into scripts, UI, or other addons.

A good HE-facing contract:

- is small and capability-oriented rather than mirroring target internals;
- uses immutable data and stable Minecraft/shared types;
- does not return internal collections, events, registries, or implementation classes;
- documents the thread and logical side for every method;
- returns `AutoCloseable`/registration tokens from subscription methods;
- never exposes the addon `CoroutineScope`, Koin, or classloader;
- can grow without forcing a breaking change.

## Mandatory target mod

When the addon is useless without the target, add its API to the compile classpath only and require a
stable public class in the descriptor.

```kotlin
repositories {
    maven("https://maven.example.com/releases")
}

dependencies {
    add("modCompileOnly", "com.example:claims-mod:4.2.0")
}
```

Use `compileOnly` instead when the publisher provides a plain Java API artifact. Never place the mod
itself in `addonLibraries` or `addonBootstrapLibraries`.

```properties
id=claims-hollow-bridge
name=Claims integration for HollowEngine
version=${version}
entry=com.example.claimsbridge.ClaimsBridgeAddon
environment=common
requiredClasses=com.example.claims.api.ClaimsApi
```

Several classes may be comma-separated. The check runs before entrypoint construction, giving a clear
log cause instead of a random `NoClassDefFoundError` inside `load()`.

`requiredClasses` checks binary presence, not mod ID or semver. If the public API exposes a version or
capabilities, validate those at the start of `load()` and fail clearly before acquiring resources.

## Bidirectional service adapter example

An addon-owned contract might be:

```kotlin
import net.minecraft.core.BlockPos
import net.minecraft.resources.ResourceKey
import net.minecraft.world.level.Level
import java.util.UUID

interface ClaimsHeApi {
    fun owner(level: ResourceKey<Level>, position: BlockPos): UUID?

    fun observe(listener: (ClaimChange) -> Unit): AutoCloseable
}

data class ClaimChange(
    val level: ResourceKey<Level>,
    val position: BlockPos,
    val oldOwner: UUID?,
    val newOwner: UUID?,
)
```

The adapter knows the target API directly but publishes only the contract above:

```kotlin
import com.example.claims.api.ClaimsApi
import net.minecraft.core.BlockPos
import net.minecraft.resources.ResourceKey
import net.minecraft.world.level.Level
import java.util.UUID
import java.util.concurrent.atomic.AtomicBoolean

class ClaimsAdapter(
    private val target: ClaimsApi,
) : ClaimsHeApi, AutoCloseable {
    private val closed = AtomicBoolean()
    private val listeners = linkedSetOf<(ClaimChange) -> Unit>()
    private val targetRegistration = target.onClaimChanged { event ->
        listeners.toList().forEach { listener -> listener(event.toHeChange()) }
    }

    override fun owner(level: ResourceKey<Level>, position: BlockPos): UUID? =
        target.findClaim(level, position)?.owner

    override fun observe(listener: (ClaimChange) -> Unit): AutoCloseable {
        check(!closed.get()) { "Claims adapter is closed" }
        listeners += listener
        return AutoCloseable { listeners -= listener }
    }

    override fun close() {
        if (!closed.compareAndSet(false, true)) return
        targetRegistration.close()
        listeners.clear()
    }
}
```

The real listener collection must follow the target event bus's threading contract, such as a
`CopyOnWriteArrayList` for concurrent callbacks or strict server-thread ownership.

The entrypoint binds that adapter to the addon lifecycle:

```kotlin
import com.example.claims.api.ClaimsApi
import kotlinx.coroutines.CoroutineScope
import ru.hollowhorizon.hollowengine.common.addons.HollowAddonContext
import ru.hollowhorizon.hollowengine.common.addons.HollowAddonEntrypoint
import ru.hollowhorizon.hollowengine.common.addons.extensions
import ru.hollowhorizon.hollowengine.common.addons.publish

class ClaimsBridgeAddon : HollowAddonEntrypoint {
    override suspend fun load(context: HollowAddonContext, scope: CoroutineScope) {
        val adapter = ClaimsAdapter(ClaimsApi.instance())
        context.extensions.onUnload(adapter::close)
        context.hostServices.publish<ClaimsHeApi>(adapter)
    }
}
```

Cleanup is registered before publishing the service. A later failure therefore closes the adapter
during rollback. The runtime removes the service automatically; manual `unpublish` is unnecessary.

A consumer addon declares `dependsOn=claims-hollow-bridge`. It then sees the exact `ClaimsHeApi`
class from the provider classloader, and the provider unloads only after its consumers.

## Optional target mod

If the addon remains useful without the target, omit its class from `requiredClasses`. Do not put
foreign types in entrypoint fields, superclass, interfaces, constructor, or method signatures. Keep
direct imports in an adapter class loaded only after checking the mod ID.

```kotlin
import kotlinx.coroutines.CoroutineScope
import ru.hollowhorizon.hollowengine.common.addons.HollowAddonContext
import ru.hollowhorizon.hollowengine.common.addons.HollowAddonEntrypoint
import ru.hollowhorizon.hollowengine.common.addons.extensions
import ru.hollowhorizon.hollowengine.common.addons.publish
import ru.hollowhorizon.hollowengine.common.utils.ModList

class OptionalBridgeAddon : HollowAddonEntrypoint {
    override suspend fun load(context: HollowAddonContext, scope: CoroutineScope) {
        if (!ModList.isLoaded("claims")) {
            context.hostServices.log("Claims integration is inactive: target mod is not installed")
            return
        }

        val adapter = runCatching(::createClaimsAdapter).getOrElse { error ->
            context.hostServices.log("Claims integration is incompatible: ${error.message}")
            return
        }
        context.extensions.onUnload(adapter::close)
        context.hostServices.publish<ClaimsHeApi>(adapter)
    }
}
```

Place `createClaimsAdapter()` in the class/file that isolates target imports. `ModList.isLoaded` does
not prove API-version compatibility; a `LinkageError` means the adapter must be updated. Do not keep
running in a partially compatible mode when data could be corrupted.

`@RequireMod` applies only to a discovered `@SubscribeEvent` handler. It is useful for one optional HE
handler, but does not isolate target classes or disable the complete entrypoint.

## Foreign events and threads

Never assume the target callback uses the server thread. It may arrive on a render thread, network
executor, worker pool, or custom scheduler.

For an asynchronous notification that can continue later:

```kotlin
targetRegistration = target.observe { targetEvent ->
    val snapshot = targetEvent.toImmutableSnapshot()
    context.minecraft.dispatchers.executeServer {
        applyToWorld(snapshot)
    }
}
```

Do not retain the original event object: it may become invalid after the callback or hold an entire
world/registry. Copy only required values.

If the event requires a synchronous return or cancellation, it cannot be dispatched asynchronously
without changing semantics. Perform a short thread-safe check in the callback or use the target's
official thread transition. Blocking a worker while waiting for the server thread risks deadlock.

Run background collectors in the provided addon scope. If a foreign library creates a private
thread/executor, the adapter must stop it in `close()`.

## Networking and logical sides

First decide where authoritative state lives:

- server integration reads and mutates target server state;
- client UI receives only an allowed snapshot;
- every client request is validated again on the server;
- packets never transport target implementation objects.

When a packet type belongs to the addon, a compatible addon must be installed on both connection
ends. A server-only bridge with no client feature may need no packet at all.

`environment` describes the **physical** side. `server` does not load in an integrated server because
that process is physically a client. A singleplayer-capable bridge normally uses a `common`
entrypoint with no unconditional client imports and separates logical server/client work explicitly.

Use the target's network API only when it is public, stable, and supports runtime registration. A
stable `HollowAddonPacket` otherwise isolates the HE contract better, at the cost of matching bridge
addon installations and versions.

## Fabric and NeoForge

The standard convention builds a named NeoForge variant and a remapped intermediary Fabric variant
from one common source set. This works well when the target publishes the same public API on both
platforms.

When APIs differ:

1. retain one common HE-facing contract;
2. isolate platform implementations;
3. never load Fabric classes on NeoForge or the reverse;
4. do not detect a platform through a random internal class;
5. use a regular multiplatform companion mod when the difference is substantial.

The current standard addon convention does not expose independent `fabric` and `neoforge` source
sets for separate adapters. Avoid complex conditional links to loader internals; thin companion
adapters are easier to verify.

## When a companion mod is required

Use a companion when integration must:

- register a block/item/entity/menu/attachment or another early object;
- install a Mixin config, access widener, or access transformer;
- subscribe in a loader phase that predates addon runtime;
- provide different Fabric and NeoForge implementations;
- reach a closed API through a supported Accessor/Invoker;
- hold a native/bootstrap dependency for the entire game process.

Then split the architecture:

```text
Fabric companion ─┐
                  ├─ parent-loaded stable BridgeContract
NeoForge companion┘                 ▲
                                    │ compileOnly
                         hot-swappable HE addon
```

Define the stable contract in the companion/API artifact loaded by the parent classloader. It must
not reference addon implementation types. The companion provides a reversible callback/service API;
the addon owns and closes registrations.

The Mixin/accessor stays active until JVM shutdown, but addon behavior remains reloadable as long as
the companion releases every callback token. This is the honest hot-swap boundary: a stable early
hook and replaceable dynamic logic.

## Versions and failure behavior

The current descriptor has no `minHostVersion`, target-mod version range, or optional `dependsOn`.
An integration addon therefore should:

- compile against the oldest supported public API;
- use official capability/feature checks;
- fail before publishing services when a mandatory capability is absent;
- store data in a versioned schema, never serialized target implementation classes;
- handle unknown future enum/packet values safely;
- test every claimed version instead of relying on compilation;
- publish compatible HE/Minecraft/target versions in release notes.

Do not add a “fallback through private reflection.” It turns a predictable incompatibility into a
hidden data error. Prefer a clear load failure with an actionable diagnostic.

## Integration checklist

Before release, test:

1. target mod absent;
2. oldest and newest claimed target API versions;
3. dedicated server, physical client, and integrated server;
4. Fabric and NeoForge;
5. a target callback racing with disable/reload;
6. repeated load/unload without duplicated listeners, commands, or services;
7. consumer addon unloading before the provider bridge;
8. persisted state migration from the previous bridge version;
9. malformed and stale client packet data;
10. target world/config/resource reload;
11. several reloads without extra threads or retained old addon classloaders;
12. mismatched companion/addon versions producing a clear failure rather than partial behavior.

The rule is simple: an addon is suited to dynamic **logic and adaptation of public runtime APIs**.
Anything that changes early game structure or lacks reversible registration belongs in a regular mod
or stable companion layer.
