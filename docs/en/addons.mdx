# Addon development

A HollowEngine addon is a JAR loaded from `hollowengine/addons` in its own classloader. It can add
Minecraft behavior, commands, packets, services, Hollow IDE panels, and editors without becoming a
regular Fabric or NeoForge mod.

The central API concept is **lifecycle ownership**. A registration made through
`context.extensions`, `context.minecraft`, or `context.hostServices` belongs to one addon.
HollowEngine removes it after a load failure, disable, reload, or unload before closing the old
classloader.

## When to use an addon, a script, or a regular mod

| Task | Choose | Why |
| --- | --- | --- |
| Quest, dialogue, cutscene, or small gameplay logic | Script | Minimal build work and fast reload |
| Commands, events, packets, services, HUD, or Hollow IDE extensions | Addon | Typed Kotlin API and managed hot-swap |
| New blocks, items, entities, menus, or other frozen registry entries | Regular mod | Registration must happen in an early loader phase |
| Mixin, access widener/transformer, coremod, or class-loading changes | Regular/companion mod | These mechanisms cannot be attached safely after JVM startup |
| Bridge between HollowEngine and another mod's public API | Addon or addon + companion | The choice depends on whether every runtime registration is reversible |

An addon is not a security sandbox. It executes arbitrary JVM code with the same privileges as
HollowEngine, Minecraft, and regular mods. Install only trusted JARs.

## Quick start

Create a project under `addons/` in the HollowEngine source tree. Every nested directory containing
a `build.gradle.kts` is discovered automatically and added to the Gradle graph.

```text
addons/my-addon/
├── build.gradle.kts
└── src/main/
    ├── java/com/example/myaddon/MyAddon.kt
    └── resources/META-INF/plugin.properties
```

Minimal `build.gradle.kts`:

```kotlin
base {
    archivesName.set("MyAddon")
}
```

The shared Gradle convention already adds Minecraft, mappings, the HollowEngine runtime, Kotlin,
coroutines, serialization, and Koin to the compile classpath.

The supported development workflow currently places the project inside the HollowEngine source
tree. There is no published standalone Gradle plugin for external repositories in the current
implementation. An independently maintained build must reproduce the root convention and universal
JAR format exactly; the loader rejects a normal Kotlin `jar` as a legacy format.

Descriptor at `src/main/resources/META-INF/plugin.properties`:

```properties
id=my-addon
name=My Addon
version=${version}
entry=com.example.myaddon.MyAddon
environment=common
```

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | yes | Stable ID using lowercase ASCII letters, digits, `_`, `-`, and `.` |
| `entry` | yes | Fully qualified class implementing `HollowAddonEntrypoint` |
| `name` | no | Display name; defaults to `id` |
| `version` | no | Version; `${version}` is expanded by the Gradle build |
| `environment` | no | `common`, `client`, or `server`; defaults to `common` |
| `dependsOn` | no | Comma-separated IDs of required addons |
| `requiredClasses` | no | Comma-separated classes checked before `load()` |

Additional descriptor rules:

- `id` cannot be empty, contain `:`, or equal the reserved `hollowengine` namespace;
- `version` defaults to `1.0.0`; it is currently informational and is used as a packaged-script
  fingerprint, not for semver resolution;
- `name` is display-only;
- `entry` must name a public class with an accessible no-argument constructor;
- `dependsOn` cannot contain the addon's own ID or duplicate IDs;
- every `dependsOn` entry is mandatory; there is no separate optional-dependency field yet;
- `requiredClasses` checks binary API visibility through the addon classloader, but not a mod ID or
  mod version.

`environment=common` means “load on both a physical client and a dedicated server,” not “client API
may be referenced unconditionally.” Use `client` for Hollow IDE, Compose, HUD, and
`Minecraft.getInstance()`. A `server` addon does not load on a physical client, including its
integrated server.

Entrypoint:

```kotlin
class MyAddon : HollowAddonEntrypoint {
    override suspend fun load(context: HollowAddonContext, scope: CoroutineScope) {
        context.hostServices.log("Loaded ${context.descriptor.id}")
    }

    override suspend fun unload(context: HollowAddonContext) {
        // Only needed for state that is not owned by a lifecycle API.
    }
}
```

## How loading works

The runtime performs this cycle for each addon:

1. Selects the bytecode variant for the active loader and mapping namespace from the universal JAR.
2. Creates an isolated classloader. Classloaders named by `dependsOn` become dependencies.
3. Creates a dedicated `Job`, `CoroutineScope`, Koin container, and owner-scoped APIs.
4. Instantiates the entrypoint and calls `load(context, scope)`.
5. Discovers `@SubscribeEvent` handlers, registers packets, and attaches addon scripts.
6. Publishes the addon as loaded only after every previous step succeeds.

If any step fails, the runtime rolls back registrations that were already created. During a normal
unload it stops scripts and the scope, calls `unload()`, removes extensions and published services,
closes Koin, and finally closes the classloader.

Two practical rules follow:

- launch background coroutines in the provided `scope`, never in `GlobalScope`;
- pass every external resource the runtime cannot see to
  `context.extensions.onUnload { ... }`.

```kotlin
override suspend fun load(context: HollowAddonContext, scope: CoroutineScope) {
    val watcher = createMyWatcher()
    context.extensions.onUnload(watcher::close)

    scope.launch {
        watcher.events.collect { event -> handle(event) }
    }
}
```

Cleanup runs in reverse registration order. You may close the returned
`HollowAddonRegistration` earlier; repeated `close()` calls are safe.

### Exact lifecycle order

During load, the runtime:

1. stages the source JAR in a SHA-256 cache and selects the current platform/mappings variant;
2. checks environment, disabled state, bootstrap libraries, and addon dependencies;
3. extracts regular libraries, creates the classloader, and checks `requiredClasses`;
4. creates the entrypoint, `SupervisorJob`, addon `CoroutineScope`, owner-scoped APIs, and Koin;
5. calls `load()`;
6. scans the variant JAR for `@SubscribeEvent` and `@HollowPacketHandler`;
7. publishes bundled scripts;
8. adds the addon to `HollowAddonManager.loaded` only after every step succeeds.

When load fails, the runtime cancels the scope, removes packets/extensions/services, and closes Koin
and the classloader. **`unload()` is not called for a partially loaded addon.** Register an external
resource with `onUnload` immediately after successfully acquiring it, before the next operation that
may throw.

Normal unload runs in this order:

1. remove the script namespace;
2. cancel the addon job and join all child coroutines;
3. remove addon packets;
4. call `unload()` with the scope already cancelled;
5. close extensions and arbitrary cleanup in reverse order;
6. close Koin, remove published services, and close the classloader.

Use `unload()` for final persistent-state writes, not to launch work in the scope received by
`load()`: that scope is already cancelled. An `unload()` failure is logged and does not prevent the
remaining cleanup steps.

## What is in `HollowAddonContext`

| Property | Purpose |
| --- | --- |
| `descriptor` | Addon ID, name, version, environment, and dependencies |
| `addonFile` | The loaded addon artifact |
| `classLoader` | Isolated classloader for the current addon version |
| `koin` | Addon Koin container and host bindings |
| `hostServices` | Typed service exchange between addons |
| `extensions` | Owner-scoped extension points and arbitrary cleanup |
| `minecraft` | Events, commands, packets, and game dispatchers |

`extensions` and `minecraft` are extension properties, so import them from
`ru.hollowhorizon.hollowengine.common.addons`.

`addonFile` points to a staged cache copy of the universal JAR, not the original file in the addons
directory. Do not modify it or store persistent state beside it. Choose a stable namespaced path such
as `hollowengine/data/my-addon/`, perform IO away from game threads, and write atomically. The current
host API has no dedicated `pluginStorage()` service.

Normal JAR resources are available through `context.classLoader.getResourceAsStream(...)`; close the
stream. Merely placing `assets/` or `data/` in an addon JAR does not make it a Minecraft resource/data
pack. Pack discovery requires a supported reload hook or a companion mod.

## Extension points and IDs

`HollowAddonExtensionPoint<T>` stores typed contributions. An addon does not supply its owner ID:
`context.extensions` is already bound to `context.descriptor.id`.

```kotlin
val fullId = context.extensions.qualify("overview")
// my-addon:overview
```

ID rules:

- local `overview` becomes `my-addon:overview`;
- `my-addon:overview` may be supplied explicitly;
- a foreign namespace is rejected;
- one extension point cannot contain the same qualified ID twice for one addon;
- contributions are sorted by descending `priority`, then registration order.

Use helpers such as `registerIdePanel` and `registerHudLayer` for standard features. The low-level
`register(point, id, value, priority)` method is intended for custom extension points.

An extension point normally belongs to the subsystem that consumes its values. If a group of addons
defines its own point, put the point and contribution types in an API addon and add its ID to every
contributor's `dependsOn`. Do not copy the same interface into several JARs: to the JVM, classes with
the same name loaded by different classloaders are different types.

## Minecraft API

### Events

`subscribe<T>()` creates an explicit synchronous subscription. The callback runs on the thread
posting the event, so it must not block. Callback failures are logged with the addon ID, and the
subscription is removed with the addon scope.

```kotlin
context.minecraft.subscribe<TickEvent.Server>(priority = 100) { event ->
    updateServerState(event.server)
}
```

Annotated handlers remain supported:

```kotlin
@SubscribeEvent
fun onServerTick(event: TickEvent.Server) {
    updateServerState(event.server)
}
```

Public entrypoint methods, Kotlin `object` declarations, static methods, and top-level functions
are discovered automatically. Explicit `subscribe` is useful for dynamically created handlers and
closures.

Annotated handlers follow strict rules:

- the declaring class and method must be public;
- the method accepts exactly one `Event` and returns `Unit`/`void`;
- an instance method may only live on the entrypoint or a Kotlin `object`;
- `@ClientOnly` skips a class/file/function on a dedicated server;
- `@RequireMod("mod-id")` skips the particular handler when the mod is absent;
- higher `priority` runs first, and the event executes synchronously on its posting thread.

Automatic scanning happens **after** `load()`. If load itself depends on an event, register it
explicitly with `context.minecraft.subscribe`.

### Commands

```kotlin
context.minecraft.registerCommands { dispatcher ->
    dispatcher.register(
        Commands.literal("my-addon")
            .executes { command ->
                command.source.sendSuccess({ Component.literal("Addon is active") }, false)
                1
            },
    )
}
```

`registerCommands` also works during hot load: the current dispatcher is replayed to the new addon.
Created Brigadier nodes are tracked and removed on unload/reload; after a server-side change, command
trees are sent to players again.

Register client commands with `registerClientCommands`. This call is only valid when the addon runs
in a client environment.

### Packets

Addon packets travel inside one stable HollowEngine payload. Their types can therefore be added and
removed at runtime without mutating Fabric or NeoForge's frozen payload registry.

```kotlin
@Serializable
data class ShowNoticePacket(val text: String) : HollowAddonPacket {
    override fun handle(player: Player) {
        // Runs on the side that received the packet.
    }
}

context.minecraft.registerPacket(
    ShowNoticePacket::class,
    HollowPacketHandler.Direction.TO_CLIENT,
)
```

After registration, send the packet through its normal methods: `packet.send(player)`,
`packet.send()`, or the tracking entity/dimension helpers. Direction is validated while sending and
receiving.

`@HollowPacketHandler` and automatic discovery remain available. Explicit registration is useful
when direction is selected in code or the type should not be handled by the annotation scanner.

The packet key is derived from the addon ID and class name. Both ends of a connection need compatible
addon versions and must register the same type with the same direction. Do not change a packet's
binary form without a protocol migration. Treat all client data as untrusted: validate sizes,
permissions, entity/resource existence, and allowed values on the server. `handle(player)` runs on
the receiving side; moving heavy work and mutations to the correct thread remains the addon's
responsibility.

### Game threads

```kotlin
val accepted = context.minecraft.dispatchers.executeServer {
    // Minecraft server thread.
}

context.minecraft.dispatchers.executeClient {
    // Minecraft render/client thread.
}
```

`executeServer` returns `false` when no active server exists. `executeClient` returns `false` on
a dedicated server or after the addon stops. A queued action checks the lifecycle again before it is
executed.

`serverOrNull()` and `clientOrNull()` return a `CoroutineDispatcher` when the corresponding game
loop is available. Launch work on them through the provided addon `scope` so cancellation propagates
to the coroutine.

The provided scope uses `Dispatchers.Default`, a `SupervisorJob`, and automatically installs the
addon classloader as the thread context classloader. One child coroutine failing does not cancel its
siblings, so every long-lived job needs intentional error handling and logging. `withContext` on
`Dispatchers.IO` is fine; manually created executors, threads, and schedulers must be closed through
`onUnload`.

## Services and Koin

`hostServices` connects addons without global mutable state:

```kotlin
interface QuestApi {
    fun start(id: String)
}

context.hostServices.publish<QuestApi>(questApi)
val api = context.hostServices.find<QuestApi>()
```

A published service is removed automatically. If its type is declared by another addon, list that
addon in `dependsOn`. The consumer classloader can then see the dependency API, and the runtime
provides correct load and unload ordering.

`find<T>()` returns the last published instance, while `findAll<T>()` returns a snapshot of all
instances. A missing service is normal during load, disable, and reload. Do not cache it in a global
singleton; resolve it again or clear the reference with the addon lifecycle.

For a durable cross-addon API:

1. put interfaces and simple DTOs in the provider/API addon;
2. declare `dependsOn=provider-addon` in the consumer;
3. do not expose the addon `CoroutineScope`, Koin types, transient Minecraft objects, or DI details;
4. evolve the contract compatibly because the descriptor does not enforce version ranges;
5. return a registration/token from callback APIs so consumers can unsubscribe.

Declare local dependencies in the entrypoint's `koinModules`. Koin already contains
`HollowAddonDescriptor`, `HollowAddonHostServices`, `HollowAddonExtensions`, and
`HollowAddonMinecraftApi`.

```kotlin
class MyAddon : HollowAddonEntrypoint {
    override val koinModules = listOf(
        module {
            single { QuestRepository() }
            factory { QuestSession(get()) }
        },
    )

    override suspend fun load(context: HollowAddonContext, scope: CoroutineScope) {
        val repository = context.koin.get<QuestRepository>()
        context.extensions.onUnload(repository::close)
    }
}
```

This is a separate Koin application, not a module in a global host Koin. Do not use exported Koin
definitions for cross-addon communication. A singleton that starts coroutines or owns a file/socket
must receive the addon scope or have explicit cleanup; removing definitions alone does not guarantee
classloader collection.

Keep `koinModules` declarative and free of external-resource side effects in its getter. An
`onUnload` callback is synchronous and must finish quickly. Use `unload()` for suspend persistence,
and also protect a partly acquired resource during a failing `load()` with local `try`/`finally`.

## Extending Hollow IDE

The IDE API is client-side. An addon importing IDE or Compose classes must declare
`environment=client` so its entrypoint is never loaded on a dedicated server.

Available helpers:

| Helper | Contribution |
| --- | --- |
| `registerIdeFileType` | Matcher, document loader, editor, and actions for a file type |
| `registerIdePanel` | Dock panel with declarative placement |
| `registerIdeMenuItem` | File, Window, Tools, or Help item |
| `registerIdeFileActions` | File-tab context menu actions |
| `registerIdeProjectActions` | Project-tree context menu actions |
| `registerIdeLanguage` | Selects a `ScriptingAnalyzer` by file path |
| `registerIdeCodeInsight` | Completion, diagnostics, inlays, definition, signature, and hover |

Built-in and addon panels/editors pass through the same registries. There is no central `when`
statement to modify for a new type.

### Panel and menu

```kotlin
override suspend fun load(context: HollowAddonContext, scope: CoroutineScope) {
    val overviewId = context.extensions.qualify("overview")

    context.extensions.registerIdePanel(
        HollowIdePanel(
            id = "overview",
            title = "My Addon",
            placement = HollowIdePanelPlacement(
                anchor = HollowIdePanelAnchor.Project,
                placement = DockPlacement.RIGHT,
            ),
            content = { ide ->
                Column {
                    Text("Focused: ${ide.focusedFile?.path ?: "none"}")
                }
            },
        ),
    )

    context.extensions.registerIdeMenuItem(
        HollowIdeMenuItem(
            id = "open-overview",
            menu = HollowIdeMenu.TOOLS,
            label = "Open My Addon",
            run = { ide -> ide.openPanel(overviewId) },
        ),
    )
}
```

`HollowIdeContext` can open a file or panel, close/query a panel, save all files, refresh the
project tree, and set a status message. Refer to addon panels by the qualified ID returned by
`context.extensions.qualify()`.

A panel `title` and menu item `label` may be literal text or a Minecraft translation key. Translation
is resolved while rendering, after the language manager is ready, so do not eagerly convert keys
with `.lang`.

### File type and editor

```kotlin
private class QuestDocument(var text: String) : HollowIdeFileDocument {
    override val readOnly = false

    override fun encode(): ByteArray = text.toByteArray()

    override fun reload(bytes: ByteArray) {
        text = bytes.toString(Charsets.UTF_8)
    }
}

context.extensions.registerIdeFileType(
    HollowIdeFileType.extensions(
        id = "quest",
        extensions = listOf(".quest"),
        priority = 100,
        loader = { _, bytes -> QuestDocument(bytes.toString(Charsets.UTF_8)) },
        editor = { file ->
            val document = file.document as QuestDocument
            Text(document.text)
        },
    ),
)
```

`loader` creates the document behind an open file, and `editor` renders it. `encode()` supplies
saved bytes; override `reload()`, `markSaved()`, and `close()` for custom state. When a file type
is removed, the IDE closes its tabs and documents before the runtime releases the addon classloader.

### Language and code insight

`registerIdeLanguage` selects a base `ScriptingAnalyzer`. `registerIdeCodeInsight` layers extra
features over the selected analyzer, allowing several addons to contribute completions and
diagnostics to the same language.

```kotlin
context.extensions.registerIdeCodeInsight(
    id = "quest-symbols",
    contributor = object : HollowIdeCodeInsightContributor {
        override fun supports(path: String) = path.endsWith(".quest")

        override fun completions(
            path: String,
            text: String,
            offset: Int,
        ): List<CompletionItem> = questCompletions(text, offset)

        override fun diagnostics(path: String, text: String): List<Diagnostic> =
            validateQuest(text)
    },
)
```

Code insight runs on a background analysis thread. Do not access Minecraft or Compose state directly
from it; use `context.minecraft.dispatchers` for game-side changes.

## HUD layers

A client addon can render relative to a vanilla HUD anchor or after the complete HUD:

```kotlin
context.extensions.registerHudLayer(
    HollowAddonHudLayer(
        id = ResourceLocation.parse("my-addon:status"),
        anchor = VanillaHudLayers.HOTBAR,
        placement = HollowAddonHudPlacement.AFTER,
    ) { render ->
        render.graphics.drawString(font, "Active", 8, 8, 0xFFFFFF)
    },
)
```

The layer ID must use the addon's namespace. The callback receives `Window`, `GuiGraphics`, and
`partialTick`, runs on the render thread, and must neither block nor retain `GuiGraphics` for later
use. `registerHudOverlay` is similar but runs after the entire vanilla HUD.

## Dependencies and packaging

### Compile-only and packaged dependencies

A dependency on HollowEngine, Minecraft, or an installed mod should normally remain compile-only.
It already exists in the game process and must not be duplicated inside the addon JAR:

```kotlin
dependencies {
    add("compileOnly", "com.example:public-api:1.0.0")
    add("modCompileOnly", "com.example:target-mod:1.21.1-4.0.0")
}
```

Choose `compileOnly` or `modCompileOnly` according to the target publication: a plain Java API uses
`compileOnly`, while a remappable Minecraft mod artifact uses Loom's `modCompileOnly`. Add the
required Maven repository in the addon's `build.gradle.kts`. Do not add another mod to
`addonLibraries`; that would create a second copy of its classes with the wrong lifecycle.

Libraries owned by the addon use these configurations:

```kotlin
dependencies {
    add("addonLibraries", "com.example:library:1.0.0")
    add("addonRuntimeLibraries", "com.example:runtime-only:1.0.0")
    add("addonBootstrapLibraries", "com.example:native-wrapper:1.0.0")
}
```

| Configuration | Compile classpath | Location in addon JAR | Notes |
| --- | --- | --- | --- |
| `addonLibraries` | yes | `hollowengine-addon-libs` | Regular addon library |
| `addonRuntimeLibraries` | no | `hollowengine-addon-libs` | Needed only at runtime |
| `addonBootstrapLibraries` | yes | `hollowengine-addon-bootstrap` | Stable classloader; changes require restart |

Do not package libraries owned by the game: Kotlin, coroutines, Koin, Log4j, LWJGL, Netty, JNA,
OSHI, or Minecraft's native stacks. The build excludes host-provided dependencies and rejects
forbidden native artifacts.

The standard `addonJar` produces **one universal JAR**. It contains a named variant for NeoForge
and an intermediary variant for Fabric; the runtime selects the correct one.

Simplified output layout:

```text
MyAddon-<version>.jar
├── META-INF/MANIFEST.MF
├── META-INF/plugin.properties
├── META-INF/hollowengine/variants/named.jar
├── META-INF/hollowengine/variants/intermediary.jar
├── hollowengine-addon-libs/*.jar
├── hollowengine-addon-bootstrap/*.jar
└── other runtime resources
```

`named.jar` serves NeoForge/official runtime; `intermediary.jar` serves Fabric production runtime.
Both contain classes and precompiled script artifacts for that namespace. The current manifest format
is `2`; a hand-built flat JAR without manifest variants is unsupported.

### How the classloader resolves classes

Each addon gets a separate child-first `URLClassLoader`, while important shared packages remain
parent-first: HollowEngine shared API, Minecraft/Mojang, core Kotlin/coroutines, SLF4J, and Log4j.
Other classes resolve in this order:

1. every `dependsOn` classloader in descriptor order;
2. the addon's variant JAR and `hollowengine-addon-libs`;
3. the parent classloader.

Consequences:

- cross-addon API types must exist in one classloader, normally the dependency/provider;
- never bundle HollowEngine, Kotlin, or Minecraft classes;
- shade and relocate private libraries with colliding packages; matching versions alone do not make
  hot-swap safe;
- `META-INF/services` and other resource registries may cache a provider classloader;
- `requiredClasses` sees host classes, addon dependencies, and packaged libraries.

The current implementation does not expose the early concept's selectable `shared-preferred`,
`strict-shared`, or other dependency policies. Resolution uses the fixed order above.

### Bootstrap libraries

`addonBootstrapLibraries` is only for a library that must be visible to a stable bootstrap/runtime
classloader before the addon loads. It is not a general dependency-conflict escape hatch. Bootstrap
JARs are validated before runtime:

- two addons may use the same library filename only when its contents match;
- conflicting classes and native resources are rejected;
- LWJGL, Netty, JNA, OSHI, and other host native stacks may not be shipped;
- adding or changing such an addon after startup produces `RESTART_REQUIRED`;
- a native library loaded into the JVM cannot be genuinely unloaded by hot-swap.

```shell
# Inspect the actual Gradle graph
.\gradlew.bat projects

# Build one addon
.\gradlew.bat :addons:my-addon:addonJar

# Build and collect every addon in build/addon-jars
.\gradlew.bat buildAddons
```

Copy the final JAR without a classifier from `build/addons/my-addon/libs/`, or the collected
artifact from `build/addon-jars/`, into the running game's `hollowengine/addons/` directory.

Do not distribute `classes-named`, `classes-intermediary`, or `variant-*` as standalone addons. The
runtime expects their outer universal JAR.

## Management and hot reload

The runtime watches `hollowengine/addons` for added, replaced, and removed JAR files.

```text
/he addons list
/he addons enable <addon-id>
/he addons disable <addon-id>
/he addons reload <addon-id>
```

Disabled IDs are persisted in `hollowengine/addons/.disabled-addons`.

An addon containing `addonBootstrapLibraries` cannot safely be replaced in a running process. It
receives the `RESTART_REQUIRED` status and loads after restart. Regular addons without bootstrap
dependencies can be hot-reloaded.

The watcher scans the directory about every two seconds. It stages the complete source JAR and
checks its SHA-256, so the runtime does not hold the build output open or read a half-written
replacement. It is still safer to build elsewhere and atomically replace the installed JAR.

| State | Meaning |
| --- | --- |
| `LOADED` | The current candidate is active |
| `DISABLED` | Its ID is stored in `.disabled-addons` |
| `RESTART_REQUIRED` | Bootstrap libraries are not present in this process |
| `WAITING_FOR_DEPENDENCIES` | A required addon is not loaded yet, or dependencies form a cycle |
| `REJECTED` | Bootstrap safety validation rejected packaged libraries |
| `INACTIVE` | The JAR is known but failed environment/class/mapping/load checks |

Reload unloads dependants safely: all direct and transitive dependants first, then the target addon.
After the new version loads, dependants load again. If it fails, the runtime attempts to restore the
previous candidate. In-memory state is not restored; important data must live outside the classloader.

Two JARs with the same `id` are ambiguous and do not load as separate versions. Remove duplicates
even when their filenames differ.

## Shipping scripts in an addon

Files under `src/main/resources/scripts/**/*.kts` are compiled during the build and placed in both
mapping variants. Scripts use the addon `id` as their namespace and can see its classes and
`addonLibraries`.

```text
/he scripting run my-addon:nodes/quest.node.kts
```

Importing another namespace requires its addon in `dependsOn`:

```kotlin
@file:Import("other-addon:shared.kts")
```

To omit script sources from the final JAR:

```shell
.\gradlew.bat buildAddons -Phollowengine.scripts.includeSources=false
```

## Limitations and common failures

- **Blocks, items, and entities.** Frozen Minecraft registries are intentionally outside the runtime
  API; they require an early bootstrap phase and a game restart.
- **Client classes on a server.** Use IDE, HUD, `Minecraft`, and Compose classes only with
  `environment=client` or behind a separate client-only boundary.
- **Classloader leak.** Do not retain addon classes in host global singletons. Register
  `onUnload` for every third-party subscription or executor.
- **Long-running work.** Do not block event, render, or server threads; use the addon `scope` and
  game dispatchers.
- **Duplicate ID.** One addon cannot register the same local ID twice in one extension point. Use
  qualified IDs when referring to contributions.
- **Dependency wait.** `WAITING_FOR_DEPENDENCIES` means a missing `dependsOn` or a dependency
  cycle. `REJECTED` usually indicates a bundled library conflict. The log and
  `/he addons list` include the reason.

### What is fundamentally not hot-swappable

- classes already modified by a Mixin/transformer, access widener/transformer, and loader entrypoints;
- frozen registries and objects whose identity Minecraft retains for the process lifetime;
- native libraries, JVM shutdown hooks, and uncontrolled third-party threads;
- registrations in another mod when its API exposes no unregister/dispose token;
- addon objects serialized by JVM class name without an explicit migration schema;
- APIs that pass an addon instance into a permanent host singleton or static cache.

### Classloader leak checklist

Before release, verify that disable/reload leaves none of these behind:

- `GlobalScope`, private `CoroutineScope`, raw `Thread`, executor, or timer;
- `ThreadLocal`, shutdown hook, JMX registration, or library-global callback;
- listener/lambda in a target mod, event bus, UI tree, open screen, or Compose state;
- HTTP client, file watcher, database pool, socket, channel, or stream without `close()`;
- service, packet type, serializer module, or ServiceLoader cache holding an addon class;
- strong reference to `context`, entrypoint, Koin, scope, or addon DTO in a host singleton.

A weak reference is not a substitute for a correct lifecycle. Prefer an explicit registration token
closed through `onUnload`.

## Testing an addon

Minimum coverage:

1. unit tests for domain logic without a Minecraft thread;
2. successful `load` and repeated cleanup/`close`;
3. failure halfway through `load` with no remaining registration;
4. disable → enable and reload with persistent-state preservation;
5. missing `dependsOn`, dependency cycle, and duplicate ID;
6. physical client and dedicated server for `common` code;
7. Fabric/intermediary and NeoForge/official variants;
8. both packet sides, wrong direction, and untrusted input;
9. missing optional target mod and an incompatible public API;
10. several consecutive reloads while checking threads/listeners/classloaders.

Run build and test commands only through the Wrapper:

```shell
.\gradlew.bat :addons:my-addon:test
.\gradlew.bat :addons:my-addon:addonJar
.\gradlew.bat buildAddons
```

After building, inspect the universal JAR as a ZIP: verify the descriptor, manifest variants,
required resources, and absence of host libraries. Compiling only one mapping variant does not
replace testing on both platforms.

## Integrating another mod

An addon can be a full runtime adapter between HollowEngine and another mod's public API: translate
events and DTOs, publish a service for other addons, add commands, IDE tools, or packets. The
architecture, mandatory and optional dependency code, threading/network rules, and companion-mod
boundary are covered in the [dedicated chapter](./addons-mod-integration.mdx).
